# 03. Bug Fixes & Improvements Log

## 1. 메인 화면 흰색(백화) 렌더링 오류 해결
- **증상**: 온보딩 완료 후 메인 홈 화면 진입 시 하단 네비게이션(BottomNav)만 보이고, 메인 콘텐츠 영역이 전체가 하얗게 나타나는 오류 발생.
- **원인**: 
  - `src/app/page.tsx` 파일 내에서 다국어 작업 및 UI 구조 변경 시, `lucide-react` 모듈에서 화면 표시에 필요한 아이콘(`Plus`, `Book`, `ArrowRight`)의 import를 누락함.
  - 이로 인해 렌더링 과정에서 `ReferenceError`가 발생하여 `page.tsx` 전체의 렌더링이 중단됨(React의 Error Boundary나 Fallback이 없어서 상위 레이아웃을 제외하고 백화 현상).
  - (추가적으로 `page.tsx` 하단에 레이아웃에 이미 존재하는 `<BottomNav />`, `<AdBlockModal />` 컴포넌트가 중복 삽입되어 `ReferenceError: BottomNav is not defined`가 발생한 것도 연관된 렌더링 오류 원인이었음)
- **해결 방안**: 
  1. 누락되었던 아이콘 컴포넌트를 import 목록에 추가.
  2. `page.tsx`를 기존 원본 UI로 복구하여 중복 삽입된 태그 및 레이아웃 충돌 문제를 해소함.

## 2. 캐릭터 생성 직후 선톡(초기 메시지) 미발송 버그 해결
- **증상**: 캐릭터 생성 직후 홈/채팅 목록에서는 "새로운 메시지가 있어요"라고 뜨지만, 막상 채팅방에 들어가보면 캐릭터의 선톡 메시지가 존재하지 않는 현상.
- **원인**: 
  - 최근 서버 사이드 채팅 API(`api/chat/route.ts`) 업데이트 과정 중, 메시지 저장 로직에 `requestId` 필드가 새로 추가됨.
  - 최초 선톡 생성 시에는 `requestId`가 `undefined` 상태로 전달되는데, Firestore의 `setDoc()` 함수는 `undefined` 값을 지원하지 않으므로 백그라운드 DB 저장 작업 중 `Unhandled Runtime Error`를 뱉으며 조용히 실패함.
  - 결과적으로 OpenRouter API를 통해 응답은 정상적으로 받아왔으나 DB 저장이 누락되었음. 반면 UI 목록은 데이터가 없을 때 기본 텍스트(`chat.newMessage`)를 띄우고 있어 마치 메시지가 온 것처럼 보였던 것임.
- **해결 방안**: 
  - `src/app/api/chat/route.ts`의 DB 저장 객체(`newMsg`) 생성 로직을 수정.
  - `requestId`가 존재할 때만 객체 프로퍼티에 포함되도록 예외 처리(`...(requestId ? { requestId } : {})`)를 추가하여 Firestore가 에러 없이 정상 저장하도록 조치 완료.

## 4. ImgBB 프로필·홈 배경 이미지 간헐 깨짐 방어

- **증상**: `dreamary` 로그인 계정에서 캐릭터·유저 프로필 사진 또는 홈 배경이 운영 웹과 앱에서 불규칙하게 깨져 보임.
- **확정 원인**:
  - 해당 계정의 이미지 URL 8개를 최소 범위로 확인한 결과 ImgBB 원본 3개가 반복해서 HTTP 404를 반환함.
  - 정상 원본도 반복 요청에서 최대 약 9초 지연 또는 10초 타임아웃이 발생함.
  - 기존 화면은 외부 이미지 실패 후 재시도·영구 로컬 캐시·대체 표시가 없어 ImgBB 장애를 그대로 노출함.
- **수정 내용**:
  1. ImgBB 저장소와 기존 Firestore URL 구조는 유지함.
  2. 정상 다운로드한 이미지 Blob을 브라우저·WebView IndexedDB에 URL 기준으로 최대 30일 보관함.
  3. 원본 표시 실패 시 로컬 캐시를 우선 사용하고, 캐시가 없으면 0.5초·1.5초 간격을 포함해 최대 3회 네트워크 다운로드를 시도함.
  4. 최종 실패 시 깨진 이미지 아이콘 대신 기본 프로필을 표시하고, 홈 배경은 실패 URL을 적용하지 않음.
  5. 최종 실패에만 Clarity `image_load_failed` 이벤트를 세션 내 URL·이미지 종류별 1회 기록함. 이미지 URL·사용자 ID는 이벤트 속성으로 전송하지 않음.
  6. Netlify `/_next/image`가 정상 ImgBB 원본에도 404를 반환한 사례가 확인되어 웹·앱 모두 Next.js 이미지 최적화 프록시를 비활성화하고 원본 또는 로컬 Blob을 직접 표시함.
- **Firebase 영향**:
  - 새 Firestore/Firebase 조회·쓰기 없음.
  - 화면이 이미 받은 이미지 URL과 IndexedDB, ImgBB HTTP 요청만 사용함.
- **검증**:
  - `npx tsc --noEmit` 성공.
  - 운영 환경 Capacitor 정적 앱 빌드 성공.
  - `npx cap sync ios`, `npx cap sync android` 성공.
  - iOS Simulator Debug 및 Android Debug 빌드 성공.
- **남은 운영 조치**:
  - 이미 ImgBB에서 404가 발생하는 원본 3개는 이전에 캐시한 기기에서만 복구 가능하므로, 원본 파일이 있으면 재업로드해 URL을 교체해야 함.

## 5. 동일 이미지 재업로드 후 기존 ImgBB 404 URL 유지

- **증상**: 엔리케 프로필 이미지를 다시 선택하고 저장했지만 저장 성공 이벤트 이후에도 기존 `FbdvggFR/IMG-0026.jpg`를 요청해 404가 계속 발생함.
- **원인 판단**: 클라이언트는 ImgBB 업로드 성공 응답의 URL을 실제 접근 가능 여부 확인 없이 저장했으며, 동일 원본 업로드가 삭제된 기존 URL로 중복 처리된 정황이 확인됨.
- **수정 내용**:
  1. ImgBB 업로드 직후 반환 URL을 실제 이미지 로딩으로 검증함.
  2. URL이 열리지 않으면 이미지 우측 하단 픽셀을 육안으로 구분되지 않게 변경해 중복 처리를 피한 뒤 한 번만 재업로드함.
  3. 재업로드 URL도 정상 로딩이 확인된 경우에만 캐릭터 문서에 저장함.
- **Firebase 영향**: Firestore 추가 조회 없음. 첫 ImgBB URL이 죽은 경우에만 ImgBB 업로드 요청이 최대 1회 추가됨.
- **검증**: `npx tsc --noEmit` 성공.

## 6. iOS 일기 장문 입력 시 스크롤·커서 추적 불가

- **증상**:
  - Android에서는 일기 textarea가 길어질수록 현재 입력 줄이 키보드 위에 유지됨.
  - iOS에서는 키보드가 열린 상태에서 일기 본문을 스크롤할 수 없고, 입력 내용이 길어져도 커서가 보이는 위치로 이동하지 않음.
- **확정 원인**:
  - 전역 Capacitor 설정이 `KeyboardResize.None`이어서 iOS WebView는 키보드가 열려도 높이가 줄지 않았음.
  - Android는 네이티브 `windowSoftInputMode`로 WebView가 축소되므로 동일한 웹 코드라도 브라우저 기본 포커스 추적이 정상 동작했음.
  - 기존 iOS 대응은 키보드 높이만큼 CSS padding을 추가하고 JavaScript로 스크롤을 보정하는 방식이었으나, 브라우저가 실제 가시 영역을 인식하지 못하는 근본 문제를 해결하지 못했음.
- **수정 내용**:
  1. iOS에서 일기 화면에 진입한 동안만 Capacitor Keyboard resize mode를 `Native`로 전환함.
  2. 일기 화면 이탈 시 기존 resize mode로 복원하여 채팅·프로필 등 다른 화면의 키보드 배치에 영향을 주지 않음.
  3. 네이티브 리사이즈 적용 시 키보드 높이를 CSS와 커서 계산에서 이중 적용하지 않도록 분기함.
  4. 일기 본문은 높이가 확정된 단일 스크롤 컨테이너로 유지하고, textarea 레이아웃 완료 후 현재 커서가 가려진 경우에만 최소 거리로 이동함.
- **Firebase 영향**: 조회·쓰기 추가 없음.
- **검증**:
  - `npx tsc --noEmit`, `npm run check:app`, iOS Capacitor 동기화 성공.
  - 연결된 iPhone 15(iOS 26.6) 대상 서명 Debug 빌드, 설치 및 앱 실행 성공.
  - 자동화 도구로 실제 기기의 터치·텍스트 입력을 제어할 수 없어 500자 입력과 손가락 스크롤의 최종 조작 검증은 사용자 실기기 확인이 필요함.
